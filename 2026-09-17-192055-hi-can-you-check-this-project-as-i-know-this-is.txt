  Current state:
  - Studio is sold via one one-time payment: early-access = Rp149.000
    (config/studio.php), which just flips has_studio_access to true forever on
    the user (app/Models/User.php line 48). No expiry field, no renewal logic

  - AI Tools (/ai-tools, the karangtools list) is currently admin-only — real
    customers hitting that route get redirected straight to Studio
    (routes/web.php:54-67). It isn't sold to anyone yet.
  - Payments go through Mayar's one-shot invoice API
    (MayarService::createInvoice). There's no subscription/recurring billing, no
    expiry check, no dunning, no "cancel plan" flow anywhere in the codebase.

  So the honest tradeoff: "subscribe 49rb/mo" isn't a pricing toggle, it's new
  infrastructure — recurring charge (via Mayar's membership API if it supports
  it, or manual monthly re-invoicing), an access-expiry field + cron to revoke
  lapsed accounts, renewal reminder emails, a manage/cancel page. None of that
  exists today, versus the one-time flow which is already built, tested, and
  shipping.

  Recommendation: don't replace the 149rb lifetime deal, split by usage pattern
  instead:
  - Studio stays one-time (149rb). People build a website once and move on,
    that's project-based usage, and it matches infrastructure you already have.
  - AI Tools becomes the new subscription product (49rb/mo). These are
    repeat-use utilities (planner, copywriter, job seeker, PDF tools), which
    fits recurring billing and lets you recover the ongoing AI API cost instead
    of eating it.
  - 69rb/mo bundle as a third option for people who want both without committing
    149rb upfront. Breakeven vs. the lifetime deal is about 2.2 months, so
    anyone who sticks around past that is a wash for you either way, and it
    doesn't cannibalize the lifetime price since it's a different commitment
    shape (rent vs. own).

  One thing to fix regardless of pricing: since both Studio and AI Tools calls
  burn real AI API cost per generation, an unmetered "lifetime unlimited" is the

● Based on what I found in Mayar's API docs (they have a real recurring
  Membership/SaaS product, not just one-off invoices), the biggest scoping
  decision is already made for you: use Mayar's native membership billing rather
  than building your own recurring-charge engine. That cuts the scope roughly
  in half. Here's the breakdown.

  Foundational decision
  Mayar's Membership product (api-reference-v2/membership/*) handles the actual
  recurring charge, grace period, and expiry itself. You register a member
  against a tier and Mayar bills them monthly; you just react to webhooks. This
  avoids building your own "charge card every 30 days" cron logic, which is the
  expensive part of DIY subscriptions.

  Pieces to build

  1. Mayar dashboard setup (no code) — create a SaaS Membership product with two
     tiers (Tools 49rb, Bundle 69rb), set grace period, register your webhook
     URL for membership events. Do this in Mayar's sandbox first.
  2. Data model (small-medium) — a new Subscription-shaped concept distinct from
     Order (which is one-time). Either a subscriptions table (user_id,
     mayar_member_id, tier, status, next_payment_at, expires_at) or columns on
     User. Given Order/has_studio_access are already modeled as one-time, I'd
     keep this separate rather than overload the existing boolean flag.
  3. MayarService additions (small) — registerMember(), cancelMember(),
     getMemberStatus() calling the v2 membership endpoints, mirroring how
     createInvoice/isPaidInvoice work today.
  4. Subscription checkout flow (medium) — a new controller parallel to
     CheckoutController that registers the member and gets the customer to
     Mayar's checkout for the first charge.
  5. Webhook handling (medium) — extend MayarNotificationController (or a new
     one) to handle membership.newMemberRegistered (grant access),
     membership.memberExpired (revoke), membership.memberUnsubscribed (mark
     canceled, access runs to expiredAt), membership.changeTierMemberRegistered
     (swap Tools ↔ Bundle). This is the part most worth testing thoroughly,
     since webhooks can arrive late or out of order.
  6. Reconciliation job (small) — a scheduled command that re-checks membership
     status against Mayar directly, same defensive pattern
     CheckoutController::finalize already uses for one-time orders (never trust
     the webhook alone). Note: no scheduler is configured at all right now
     (bootstrap/app.php has no withSchedule, and there's no server cron calling
     schedule:run), so this is new infrastructure, not just a new command.
  7. Access gating (medium) — today EnsureStudioAccess checks a static boolean.
     Subscription access needs a time-bound check (status === active && now() < 
     expires_at), and you need to open the currently admin-only /ai-tools route
     to tools/bundle subscribers. Bundle subscribers also need to pass the
     Studio gate alongside the existing lifetime buyers.
  8. Self-service management page (small-medium) — where a subscriber sees their
     tier/next payment date and can cancel (calling Mayar's cancel endpoint,
     access continues until expiredAt rather than instant cutoff).
  9. Emails (small) — subscription-welcome mail parallel to StudioAccessMail,
     maybe a cancellation confirmation.
  10. Admin visibility (small) — extend the admin orders-style panel to list
      active/expired/canceled members.
  11. Usage caps (worth bundling in, medium) — since both Studio and AI Tools
      cost you real API money per generation, I'd add a per-period generation
      cap now rather than retrofit it later, reusing ToolHistory to count usage.

  Open questions to verify before building (5-10 min of checking, not guessing):
  - Exact base path for membership endpoints (the existing invoice call uses
    /hl/v2/invoices/..., need to confirm whether membership lives under the same
    /hl/v2/ prefix or a different host, since the docs I found are versioned
    api-reference-v2 separately from the hl/v2 prefix already in your code).
  - Whether payment.received also fires for recurring renewal charges (docs
    didn't show a dedicated "renewal succeeded" event), which affects whether
    the reconciliation job or the webhook is your source of truth for "still
    paying."
  - Whether Mayar's sandbox (mayar.club) supports memberships for testing, same
    as it does invoices.

  Net effect: items 2-7 are the real new build (data model, service calls,
  webhook handling, time-based gating). 8-11 are smaller and could ship in a
  fast-follow. Want me to start with the data model + MayarService additions, or
  do you want to nail down the sandbox/webhook questions with Mayar first?

● Yes, and you don't need a second codebase to get it. Two real options, worth
  being clear about the tradeoff:

  Option A: Same Laravel app, subdomain-based routing (recommended)
  Laravel supports domain-scoped route groups natively:
  Route::domain('aitools.karanglabs.cloud')->group(function () {
      // AI Tools subscription site: its own landing page, checkout, dashboard
  });

  Route::domain('karanglabs.cloud')->group(function () {
      // Studio: everything currently in web.php stays here
  });
  - Session/accounts stay separate automatically. Your SESSION_DOMAIN is
    currently unset (.env.example:34), which means cookies scope to the exact
    host. karanglabs.cloud and aitools.karanglabs.cloud will naturally get
    independent sessions without any extra config, i.e. two genuinely separate
    "sites" from a login/access standpoint, even though it's one codebase. If
    you ever want to merge later (single login across both), that's a one-line
    change (SESSION_DOMAIN=.karanglabs.cloud), not a rewrite.
  - One deploy, one DB, one Mayar webhook receiver, reuse of MayarService/User
    model/AI provider clients you already built. This matters a lot for a
    solo-maintained project, since separate apps means duplicating auth,
    billing, and every AI integration.
  - Only new infra needed: a DNS record for the aitools subdomain pointing at
    the same server, and a cert covering it (wildcard cert or an extra Let's
    Encrypt entry, most hosts including Laravel Cloud handle additional domains
    without much friction).
  - If you want it to look like a distinct product (different branding, no
    Studio nav bleeding in), that's just a separate landing page + layout under
    the domain group, not a separate deploy.

  Option B: Fully separate second Laravel app/repo/DB for 
  aitools.karanglabs.cloud
  True isolation, independent deploys, could even fail/scale independently of
  Studio. But you'd duplicate auth, the Mayar integration, admin tooling, and
  every AI tool's backend logic, and you'd need to build something (shared API
  or SSO) if you ever want a user's login to work across both. For a project
  this size, that's a lot of ongoing double-maintenance for separation you can
  already get with Option A's session behavior.

  My take: go with Option A. It gives you exactly what you're asking for, a
  separately-branded, separately-priced, separately-authenticated subdomain,
  without doubling your infrastructure or forking the codebase.

● Here's what the Planner tool actually is and how it works:

  What it is
  Despite what the tool-card description says elsewhere in the app ("organize
  your day, track your goals..."), it's not a to-do/task planner. It's a
  product-idea-to-build-plan generator: you describe a raw app idea in free
  text, and it turns that into a full product plan plus a ready-to-paste prompt
  for Claude Code/Cursor/etc. to start building it.

  How it works, end to end (resources/js/Components/StepWizard.jsx +
  GeneratePlanController):

  1. Step 1 - Idea. You type a free-text description of what you want to build
     (there's an "Isi Acak" button that fills in one of 3 sample ideas so you
     can see it work).
  2. Step 2 - Tech stack preference. Three modes: let AI decide, pick per layer
     (frontend/backend/database/deployment dropdowns), or type your own custom
     stack.
  3. Step 3 - Dynamic clarifying questions. On advancing to this step, it fires
     a separate call to /api/generate-questions (GenerateQuestionsController),
     which asks Claude to generate exactly 5 questions tailored to your specific
     idea (audience, core action, must-have features, differentiator,
     retention), each rendered as single-select, multi-select, or free text. All
     optional, skippable.
  4. Generate. Everything (idea + tech preference + your answers) posts to
     /api/generate-plan (GeneratePlanController), which builds one big prompt
     and calls Claude (claude-sonnet-4-6) with a system prompt instructing it to
     return exactly 4 JSON fields:
     - summary - 2-3 sentence plain-language pitch
     - feature_map - features grouped by build phase
     - prd - a full PRD (overview, target users, KPIs, feature breakdown with
       user stories/acceptance criteria, technical requirements, risks,
       timeline)
     - ai_prompt - a ready-to-paste prompt for an AI coding tool, including tech
       stack, features with acceptance criteria, folder structure, and "build
       step by step starting with data model and auth"
  5. The controller cleans up the response (strips markdown fences, fixes
     truncated/invalid JSON with fallback repair attempts, strips control
     chars), saves it to tool_histories tied to your user + planner slug, and
     returns it.
  6. The page renders the result via OutputView, and past generations show up as
     a history list on the page (last 10, per-user, server-persisted, not
     device-local).
